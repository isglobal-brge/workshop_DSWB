Federated OMOP analysis with dsOMOP

A hands-on tutorial — exploring real hospital data across three sites, without the data ever leaving them

Download the R script (.R) Source (.Rmd)

Welcome

In this tutorial you will analyse real-world hospital data that lives in three different hospitals at once — and you will do it without ever seeing or downloading a single patient’s record.

  • OMOP CDM is a standard shape for health data: every hospital stores patients, diagnoses, drugs and labs in the same tables (person, condition_occurrence, drug_exposure, measurement, …).
  • DataSHIELD is the safety layer: you send commands, each hospital runs them on its own data and returns only aggregated, non-disclosive results.
  • dsOMOP is the bridge that lets DataSHIELD speak OMOP.
ImportantA small demo dataset — what to expect

We work with a very small sample of OMOP CDM data (MIMIC, ~100 patients per site). Two consequences worth setting up front:

  • Privacy thresholds will bite often. Every result is checked by a disclosure filter on each server, and anything describing too few patients is withheld. On a tiny cohort these patient-count thresholds are reached easily, so some operations — narrow filters, rare concepts — may return nothing. On a large, real dataset this rarely happens; it is a property of the sample size, not a fault.
  • Expect weak associations. With so few patients the analyses are underpowered, so effects are often small or non-significant. Again: a consequence of the demo’s size, not of the method.

We work with MIMIC (an intensive-care database, ~100 patients here): connect → explore → learn the recipe for building analysis tables → filter → and finish with a real regression model.

Before you start: update dsOMOPClient

These machines already have devtools, so update the client to the latest version before anything else. Force the upgrade so it reinstalls even when a version is already present:

devtools::install_github("isglobal-brge/dsOMOPClient", force = TRUE)

If R already had dsOMOPClient loaded, restart the session afterwards, then carry on.

1. Connecting to the federation

library(DSI)
library(DSOpal)
library(dsBaseClient)
library(dsOMOPClient)
builder <- DSI::newDSLoginBuilder()
builder$append(server = "nairobi", url = "https://nairobi.datashield.live",
               user = "ethiopia", password = "P@ssw0rd", profile = "omop")
builder$append(server = "douala",  url = "https://douala.datashield.live",
               user = "ethiopia", password = "P@ssw0rd", profile = "omop")
builder$append(server = "dakar",   url = "https://dakar.datashield.live",
               user = "ethiopia", password = "P@ssw0rd", profile = "omop")
conns <- DSI::datashield.login(logins = builder$build())

ds.omop.connect(resource = "omop_demo.mimic", symbol = "omop", conns = conns)
WarningAlways select a profile

The #1 beginner mistake is not selecting a profile at login. A DataSHIELD server can host several profiles (each a different set of installed packages), and the default profile here does not include dsOMOP. On these machines dsOMOP lives in the omop profile, so we pass profile = "omop" — without it, the ds.omop.* functions aren’t available.

ImportantHow to read this
  • The first argument ("measurement") is the table we look in; concept_id = 3022318 is the measurement; value_as_concept_id is the column we count. (For a social fact you’d look in "observation" instead.)

  • “No matching concept” (value 0) is OMOP’s reserved label for records whose value didn’t map to a standard concept — not suppression and not a bug.

7. The recipe: building analysis tables

To model anything we need one row per patient and one column per variable. You describe that table with a recipe; the servers build it for you. Every recipe has the same shape — here is the skeleton (don’t run this; it’s a template):

omop_recipe(
  variables = list(    # WHAT columns you want
    omop_variable(),       # a person column, or something built from a concept_id
    omop_variable_age(),   # the patient's age
    omop_variable()        # ...add as many as you need
  ),
  filters = list(),    # OPTIONAL: restrict the population (Section 8)
  output  = omop_output()  # the table SHAPE you want (usually wide = one row/patient)
)
recipe_execute()       # build it on each server into a named symbol

7.1 Start simple — sex and age

rec0 <- omop_recipe(
  variables = list(
    omop_variable(table = "person", column = "gender_concept_id", format = "sex_mf", name = "sex"),
    omop_variable_age(name = "age", year = 2024)
  ),
  output = omop_output(name = "study", type = "wide")
)
recipe_execute(rec0, out = c(study = "M0"), symbol = "omop", conns = conns)

7.3 One recipe, several tables

8. Filtering at extraction

Often you only want a subpopulation. Add a filters element so the servers only build the rows you ask for. Filters can only ever shrink a population, so they are safe. Here: patients aged 50+ who have hyperlipidemia:

rec_sub <- omop_recipe(
  variables = list(
    omop_variable(table = "person", column = "gender_concept_id", format = "sex_mf", name = "sex"),
    omop_variable_age(name = "age", year = 2024)
  ),
  filters = list(
    older       = omop_filter_age(min = 50, year = 2024),
    with_lipids = omop_filter_has_concept(concept_id = 432867, table = "condition_occurrence")
  ),
  output = omop_output(name = "study", type = "wide")
)
recipe_execute(rec_sub, out = c(study = "SUB"), symbol = "omop", conns = conns)

Combine criteria — AND, OR, and nesting

Listing several filters combines them with AND. For OR (or any nested logic) wrap them in omop_filter_group(). Here, patients who have hypertension OR hyperlipidemia — a union, so this cohort is larger than either diagnosis on its own:

rec_or <- omop_recipe(
  variables = list(
    omop_variable(table = "person", column = "gender_concept_id", format = "sex_mf", name = "sex"),
    omop_variable_age(name = "age", year = 2024)
  ),
  filters = list(
    cardiometabolic = omop_filter_group(
      omop_filter_has_concept(concept_id = 320128, table = "condition_occurrence"),  # hypertension
      omop_filter_has_concept(concept_id = 432867, table = "condition_occurrence"),  # hyperlipidemia
      operator = "OR"
    )
  ),
  output = omop_output(name = "study", type = "wide")
)
recipe_execute(rec_or, out = c(study = "ORC"), symbol = "omop", conns = conns)
ds.dim("ORC", datasources = conns)

Switch operator = "OR" to "AND", or nest omop_filter_group()s inside each other, to express any combination.

TipFiltering is a whole query language

These cover the OMOP model, and every one only ever shrinks the population (so all are disclosure-safe):

  • Person: omop_filter_sex(), omop_filter_age(), omop_filter_age_group()
  • Diagnoses / drugs: omop_filter_has_concept(), omop_filter_not_has_concept(), omop_filter_concept_count()
  • Measurements: omop_filter_has_measurement(), omop_filter_missing_measurement(), omop_filter_value() (numeric threshold), omop_filter_value_concept()
  • Time & utilisation: omop_filter_date_range(), omop_filter_visit_count(), omop_filter_prior_observation(), omop_filter_followup()
  • Combine: omop_filter_group(..., operator = "AND" | "OR"), nested to any depth
